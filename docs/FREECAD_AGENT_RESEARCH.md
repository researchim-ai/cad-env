# FreeCAD environment для обучения LLM и VLM

Исследование от 3 ноября 2026 года. Репозиторий: `cad-env`, исходный HEAD `9bc3b0f`. Ниже отдельно обозначены наблюдения по коду, результаты проверок и предлагаемые решения. Реальный FreeCAD в этой сессии не установлен; геометрические эксперименты и обучение моделей не проводились.

> Это исходный снимок до реализации. Актуальное состояние, команды и результаты проверок описаны в [LEARNING_PIPELINE.md](LEARNING_PIPELINE.md).

## 1. Рекомендуемое направление

Развивать проект как **исполняемое окружение FreeCAD и фабрику проверенных траекторий**. Его основная ценность — возможность воспроизводимо построить, увидеть, изменить и проверить параметрическую деталь.

Приоритеты:

1. Настоящий FreeCAD worker, единый протокол действий и независимый геометрический verifier.
2. Процедурная генерация параметрических деталей и запись всех промежуточных состояний.
3. Из этих состояний — текстовые задания, изображения, задачи редактирования и исправления ошибок.
4. SFT по проверенным решениям; затем сбор решений teacher-моделей, preference learning и RL.
5. Отдельный GUI-режим для обучения computer-use агентов.

Не следует начинать с массового увеличения существующего JSON или с большого RL-запуска: текущие признаки успеха не доказывают правильность CAD. Сначала нужен измеримый небольшой benchmark.

## 2. Что уже есть в проекте

### Полезные заготовки

- `cad_env/core/environment.py`: жизненный цикл документа, история команд, reset. Можно сохранить концепцию фасада окружения.
- `cad_env/core/freecad_wrapper.py`: попытка подключения Python binding и операции с документами. Нужна замена диспетчеризации действий.
- `cad_env/code_generator/`: шаблоны FreeCAD Python, генерация наборов примеров, синтаксическая проверка и subprocess executor. Полезно как стартовый материал для небольшой библиотеки эталонных программ.
- `cad_env/api/cad_api.py`: FastAPI-оболочка; может стать сервисом управления эпизодами после разделения сессий и исправления статусов.
- `cad_env/training/`: начальная подготовка текстовых пар и Hugging Face trainer. Подходит как демонстрация, но требует нового формата данных и метрик.
- `tests/`, `examples/`, документация: есть быстрые проверки интерфейсов и примеры использования.

`LLMInterface` и `FreeCADCodeGenerator` сейчас используют правила/регулярные выражения; наличие слова LLM в названии не означает вызов языковой модели. В проекте нет полноценного `step()`-контракта, пространств действий/наблюдений, task sampler, reward, рендера наблюдений или GUI recorder. Импорт `gym` в зависимостях сам по себе этого не добавляет.

### Критические расхождения между интерфейсом и реальным выполнением

**Ложноположительный успех.** `CodeExecutor._execute_simulation()` возвращает `success=True` независимо от исполнимости кода. Проверено на `this is invalid python !!!` и `raise RuntimeError("broken")`: оба получили успех. Такой backend допустим для smoke-тестов транспорта, но его результаты должны иметь `validated=False` и никогда не становиться положительными training labels.

**Действия не связаны с FreeCAD API.** `FreeCADWrapper.execute_command()` вычисляет `eval("self.freecad." + command)`. Команда `create_box` из интерфейса не реализована как соответствующий обработчик построения объекта. `kwargs` передаются в locals для `eval`, а не как аргументы вызова. Нужен явный registry типизированных операций. Произвольные выражения также мешают изоляции и воспроизводимости.

**Внешние статусы скрывают ошибку.** API `/commands/execute` и методы `LLMInterface` могут вернуть наружу `success=True`, даже если вложенный результат содержит ошибку. В будущем транспортный статус, статус исполнения и успех инженерной задачи должны быть разными полями.

**Backend выбирается ненадёжно.** Executor сначала проверяет `import FreeCAD` в Python управляющего процесса, затем запускает бинарник `freecad -c`. Эти две среды могут иметь разные установки или не совпадать вообще. Следует обнаруживать явно настроенный executable worker, запускать self-test и возвращать capabilities. Успешный exit code тоже недостаточен: нужно проверять структурированный результат worker и открываемый итоговый файл.

**Операции зависят от неявного состояния.** Шаблоны используют `doc.Objects[-1]` и `[-2]` вместо явных ссылок на целевые feature/body. После усложнения дерева это становится неверным выбором. Для отдельных фрагментов не создаётся `doc`. Полные сценарии обращаются к `FreeCAD.Gui`, что требует отдельного решения для headless-исполнения.

### Проверенные ошибки генерации

- «Создай коробку размером 10x5x3» → `intent=unknown`, код состоит из комментариев, `success=True`. Причина: проверяется подстрока «коробка», а во входе «коробку».
- «Создай конус с радиусом основания 15.2 и высотой 18.5» → `Radius1 = 5`. Радиус не извлекается в `radius1`.
- «Перемести объект на 12 единиц по оси X» → `FreeCAD.Vector(0, 0, 0)`. Извлечённый `distance` не преобразуется в координаты.
- «Увеличь объект в 1.5 раз» → `scale_factor = 2`. Коэффициент из текста теряется.
- «Создай скругление радиусом 2» → неизвестная команда, хотя шаблон скругления существует.
- Шаблон поворота переводит угол в радианы перед `FreeCAD.Rotation(axis, angle)`. Это требует исправления: данный интерфейс принимает угол в градусах; соответствие результата следует закрепить реальным integration-тестом. [Описание Rotation API авторами FreeCAD](https://blog.freecad.org/2023/01/16/the-rotation-api-in-freecad/).

Последние замечания об API и исполнимости шаблонов основаны на чтении кода/документации; фактические B-Rep результаты здесь не измерялись.

## 3. Аудит существующего датасета

Источник: `training_data/training_dataset.json`, локальный разбор всех записей.

- Всего **200 записей**: 100 базовых, 50 сценариев, 50 записей категории validation.
- **87 уникальных описаний**.
- **59 уникальных строк кода**, если брать `generated_code`, а при его отсутствии — `full_script`. Это текстовая уникальность, не число уникальных геометрий.
- **68 записей** имеют `generated_code`, состоящий только из комментариев с неизвестной командой.
- Ещё **47 сценариев** содержат такой комментарий внутри `full_script`.
- Всего **115/200 = 57,5%** записей содержат маркер неизвестной команды. Это обнаруженный дефект; оставшиеся 85 записей не были признаны геометрически корректными.
- У **50 сценариев отсутствует `generated_code`**. `LLMTrainer.prepare_training_data()` безусловно читает это поле и при обработке такого списка получит `KeyError`.

`TrainingDataManager` смешивает обычные примеры, сценарии и «validation» в один список. Последняя категория не является независимой валидационной выборкой. Повторяющиеся шаблоны при случайном разбиении могут попасть в разные splits и завысить оценку.

Аугментация также меняет смысл: «цилиндр» заменяется на «труба», хотя труба требует полости. Геометрический intent нельзя расширять произвольным словарём синонимов.

**Решение:** оставить текущий JSON как legacy fixture для регрессионных проверок, а новый корпус строить заново после проверки pipeline. Не использовать текущий набор как gold supervision.

## 5. Три подхода к действиям агента

### A. Типизированные CAD tools — лучший первый этап

Агент вызывает `create_sketch`, `add_geometry`, `add_constraint`, `pad`, `pocket`, `revolve`, `set_parameter`, `inspect`, `render`, `save`, `undo`, `finish`.

Преимущества: наблюдаемые шаги, проверяемые аргументы, хорошие labels для tool calling, простая локализация ошибки. Цена: необходимо поддерживать ограниченный набор операций и явно определять семантику каждой.

Важно не свести всё к `create_flange(parameters)`: такие макрокоманды полезны для генератора эталонов, но обходят навыки sketch/constraints/features, которым обучаем агента.

### B. Python-код FreeCAD — второй режим того же ядра

Агент пишет небольшую программу или патч и запускает её в worker. Это удобно для code LLM и позволяет использовать API шире, чем первоначальный registry. Потребуются контекст существующего документа, ограничение ресурсов, отдельный процесс/контейнер и сохранение артефактов.

Рекомендуется поддерживать и structured actions, и raw Python; сравнивать их на одинаковых задачах. В labels сохранять исходный код, реально исполненные изменения документа и проверенный результат. Не пытаться автоматически восстановить точную последовательность CAD-действий из произвольного Python AST.

### C. GUI computer use — самостоятельный трек

VLM получает скриншот и действует мышью/клавиатурой. Нужны VM snapshots, фиксированный desktop, активный workbench, selection, камера, модальные окна и ожидание завершения операций. Покрывает навыки выбора граней, ограничения эскиза и навигацию по UI.

API-траектория не превращается автоматически в GUI-демонстрацию. Для GUI labels действия надо **реально воспроизвести в GUI**, записать экран до/после и подтвердить состояние документа. В строгом GUI benchmark отключать Python console и другие обходные каналы; в гибридном режиме явно разрешать их и считать результаты отдельно.

Моя рекомендация: A+B для первой фабрики данных; C после стабильного verifier, либо раньше, если главная исследовательская цель — именно владение интерфейсом FreeCAD.

## 6. Работы и данные, на которые стоит опереться

### CADWorld: ориентир для GUI

Проект использует Ubuntu VM, скриншоты и `pyautogui`, а сохранённый FreeCAD-файл оценивает на host. В документации есть диагностика ошибок по артефактам и траекториям. Подходит как внешний GUI benchmark и источник архитектурных решений для reset/record/evaluate. Это не готовая фабрика наших параметрических SFT-данных. [Репозиторий CADWorld](https://github.com/Zdong104/CADWORLD).

### Parametric CAD Bench V3 и freecad-validator: ориентир для API/Python

V3 содержит 100 задач: 30 создания по тексту, 30 создания с последующим редактированием, 40 восстановления по инженерным чертежам. Использует закреплённую среду FreeCAD и отдельный verifier. Полезен как внешний тест. Данные публичного benchmark необходимо исключать из обучающего корпуса вместе с производными. [Описание запуска V3](https://www.gnucleus.ai/cad-bench/benchmark).

`freecad-validator` оценивает геометрию и соответствие спецификации без LLM-судьи. Его стоит проверить как подключаемый evaluator, а не сразу писать весь scorer заново. Авторы подчёркивают необходимость закреплять конкретную сборку FreeCAD/OCCT. Совместимость с нашими типами задач и устойчивость метрик ещё нужно проверить экспериментом. [Код и документация](https://github.com/gNucleus-AI/freecad-validator).

В `gnucleus-ai/cad-gen-freecad` на момент просмотра 100 строк с описаниями, параметрами, картинками и путями FCStd; карточка указывает Apache-2.0. Это небольшой native FreeCAD ориентир для инспекции формата. До любого обучения проверить пересечение с benchmark, происхождение файлов и лицензию конкретной версии. [Карточка данных](https://huggingface.co/datasets/gnucleus-ai/cad-gen-freecad).

### DeepCAD и Text2CAD: история построения и текст

DeepCAD даёт CAD construction sequences; его представление ограничено sketch/extrude, поэтому не покрывает все workbench FreeCAD. Text2CAD добавляет около 660 тысяч текстовых аннотаций к примерно 170 тысячам моделей, включая разные уровни детализации. Использовать для экспериментов с текстовыми заданиями и импорта поддерживаемых операций в нашу промежуточную схему. [DeepCAD](https://github.com/rundiwu/DeepCAD), [статья Text2CAD](https://arxiv.org/abs/2409.17106), [код Text2CAD](https://github.com/SadilKhan/Text2CAD).

Это не native FreeCAD траектории: нужны преобразование координат, единиц, профилей и булевых операций, затем replay и сравнение геометрии. STEP-импорт может дать цель для сравнения, но не восстанавливает историю проектирования.

### CAD-Recode, cadrille и CADFusion: мультимодальность и обратная связь

CAD-Recode показывает обучение на миллионе синтетических CAD последовательностей, представленных Python-кодом; его выход использует CadQuery. Это аргумент в пользу процедурного генератора, но не готовый FreeCAD backend. [Статья](https://arxiv.org/abs/2412.14042), [репозиторий](https://github.com/filaPro/cad-recode).

`cadrille` объединяет изображения, point clouds и текст с генерацией CadQuery. В README доступны SFT training/inference и веса, но прямо указано отсутствие кода RL fine-tuning. Использовать как multimodal baseline и образец подготовки данных, учитывая перенос между CAD API. [Репозиторий cadrille](https://github.com/col14m/cadrille).

CADFusion чередует обучение последовательностям CAD и обучение с визуальной обратной связью. Полезная идея для второго этапа: поощрять результат после построения и рендера. Для инженерных размеров визуальную обратную связь следует дополнять численным verifier. [Официальный репозиторий CADFusion](https://github.com/microsoft/CADFusion).

### SketchGraphs, Fusion 360 Gallery и ABC

SketchGraphs содержит 15 миллионов эскизов с графами геометрических ограничений. Полезен для constraint completion, восстановления отношений и обучения эскизным операциям; полноценного 3D решения сам по себе не даёт. [Официальный репозиторий](https://github.com/PrincetonLIPS/SketchGraphs).

Fusion 360 Gallery reconstruction включает 8 625 последовательностей sketch/extrude; другие поднаборы содержат сегментацию и сборки. Подходит для структуры построения, но требует конвертации API. Лицензия датасета ограничивает использование некоммерческими исследованиями и отдельно регулирует распространение. [Описание](https://github.com/AutodeskAILab/Fusion360GalleryDataset), [лицензия данных](https://github.com/AutodeskAILab/Fusion360GalleryDataset/blob/master/LICENSE.md).

ABC содержит миллион CAD-моделей для геометрического обучения. Рассматривать как источник B-Rep/поверхностей, изображений, point clouds и целевой геометрии; не предполагать наличие готовой FreeCAD feature history. [Сайт авторов ABC](https://deep-geometry.github.io/abc-dataset/).

Для всех источников фиксировать dataset revision, исходный ID, происхождение и условия использования. Лицензия кода не заменяет лицензию датасета. Большие корпуса в рамках этого исследования не скачивались и не воспроизводились; наличие ссылок на загрузку не равнозначно проверке всех файлов.

## 7. Предлагаемая архитектура окружения

### Исполнение и состояние

`TaskSpec` задаёт вход, начальный документ, разрешённые действия, ограничения, бюджет и evaluator contract. `CADEnv.reset(task_id, seed)` создаёт изолированный эпизод. `step(action)` возвращает observation, reward, terminated, truncated, info. `render()` и `export()` — отдельные операции. Совместимость с Gymnasium полезна как адаптер; сам контракт должен поддерживать текст, изображения и переменные структуры, а не искусственно упаковывать всё в фиксированный числовой вектор.

Предлагаемые компоненты:

- `backends/freecad_worker`: FreeCAD и работа с документом в отдельном процессе; parent не требует `import FreeCAD`.
- `actions/`: схемы аргументов, preconditions, dispatch и результат каждого действия.
- `observations/`: сжатое дерево документа, feature parameters, ошибки, selection и разрешённые изображения.
- `tasks/`: семействa задач и независимые acceptance checks.
- `rendering/`: снимки GUI и отдельные чистые рендеры геометрии.
- `evaluation/`: trusted verifier, не изменяемый агентом.
- `data/`: генератор, recorder, дедупликация, splits, экспорт JSONL.
- `training/`: адаптеры SFT/preference/RL поверх стабильных данных.

Для масштабирования — пул workers, один активный документ/эпизод на worker. Сначала новый процесс на эпизод; persistent workers добавлять после измерения затрат запуска и надёжности reset. CAD-операции внутри одного документа выполнять последовательно. После crash/timeout убивать группу процессов, сохранять диагностику и стартовать чистый worker.

### Наблюдение для LLM

Дерево объектов с логическими ID, типом, зависимостями, параметрами и состоянием recompute; единицы и placement; список тел; доступные операции; результаты измерений; короткая история действий и структурированные ошибки.

Ссылки на грани/рёбра требуют отдельного контракта: голые `Face3`/`Edge7` могут измениться при перестроении. Для генерируемых задач хранить логический feature ID, геометрический selector и соответствие в конкретном checkpoint; после изменения параметров проверять, что selector однозначно разрешается. Не считать индексы стабильными между разными версиями документа. Для задач выбора грани полезно получать supervision через picking/ID pass, связанный с камерой, и отдельно хранить такие teacher labels вне входа тестируемого агента.

### Наблюдение для VLM

Те же разрешённые текстовые поля плюс одно или несколько изображений, camera intrinsics/extrinsics, проекция, viewport resolution и соответствие кадра номеру шага. Для GUI — именно скриншот приложения; для image-to-CAD — целевой рендер или чертёж и отдельно рендер текущего решения.

Point cloud — дополнительная модальность, а не обязательная часть обычного VLM. Для неё нужен поддерживающий её encoder либо явное преобразование представления.

### Условия воспроизводимости

Закрепить image digest, FreeCAD build, OCCT, Python, workbenches, locale, единицы и tolerances; для рендера — backend, размер кадра и камеру. Headless geometry и GUI rendering разделить: наличие console API не гарантирует наличие view providers. [Официальная документация FreeCAD о headless](https://github.com/FreeCAD/FreeCAD-documentation/blob/main/wiki/Headless_FreeCAD.md).

`backend=mock` должен включаться явно. При `backend=freecad` отсутствие ядра — ошибка запуска. Для произвольного Python использовать отдельный контейнер с лимитами CPU/RAM/time, без доступа к reference/validator и ключам. Это также защищает честность reward.

## 8. Как генерировать данные

### Основной pipeline: программа → CAD → проверка → мультимодальные задания

1. Сэмплировать семейство детали, параметры, топологию и seed с выполнением геометрических ограничений.
2. Сформировать типизированную промежуточную программу: sketches, constraints, operations, references, units.
3. Детерминированно скомпилировать её в native FreeCAD sketch/features и исполнить.
4. На каждой смысловой операции записать action, входное и выходное состояние, ошибки, время и checkpoint.
5. Проверить конечную форму, требования и сохранённый FCStd в свежем процессе.
6. Получить виды, masks/depth при необходимости и параметрические чертежи.
7. Из одного источника параметров получить тексты заданий; LLM использовать для формулировок, сохраняя точные числа и смысл.
8. Валидировать соответствие текста спецификации, отфильтровать дубликаты и разнести связанные примеры по одному split.
9. Экспортировать разные представления для SFT, VLM, repair и RL.

Сначала структурированная спецификация, затем код и текст. Генерация описания с последующим regex-парсингом обратно в параметры создаёт ненужный источник ошибок, уже видимый в проекте.

### Начальные семейства

Начать с пластины с отверстиями, втулки, фланца, ступенчатого вала, L-кронштейна, кармана/корпуса и линейных/круговых массивов. Для каждой детали задать допустимые интервалы и зависимости: толщина стенки положительна, отверстия не пересекают край, диаметры согласованы, pocket не уничтожает тело.

Сложность увеличивать через число features, разные плоскости/ориентации, слепые и сквозные отверстия, constraints, зависимости размеров, fillet/chamfer и редактирование upstream параметров. Поток случайных размеров одной коробки даёт много строк, но мало новых навыков.

### Какие обучающие задачи получать

- **Text → CAD:** описание и ограничения → программа или tool calls.
- **Partial document → next action:** текущая модель и цель → следующая операция.
- **Edit:** исходный FCStd и требование изменить параметр → минимальные действия с сохранением остальных свойств.
- **Repair:** испорченная программа/документ, ошибка и изображение → исправление. Сохранять реальную причину и результат повторной проверки.
- **Image → CAD:** несколько видов → модель; для единственного вида не требовать невидимых деталей или точного абсолютного масштаба без опоры.
- **Drawing → CAD:** проекции, размеры и сечения → модель. Нужна проверка размерных линий и соответствия обозначений геометрии; это отдельная сложность, которую добавляем после простых рендеров.
- **Grounding:** изображение с выделением грани/ребра → логический объект и операция.
- **Inspection/QA:** измерить отверстие, объяснить диагностическую ошибку, проверить конкретное требование.
- **GUI trajectories:** скриншоты → click/type/hotkey с подтверждёнными переходами состояния.

У каждого derivative сохранять parent model ID. Несколько видов одной детали — не несколько независимых CAD-примеров.

### Четыре источника траекторий

**Процедурный expert.** Дешёвый и проверяемый основной источник; обязательно варьировать структуру и стратегии, а не только числа.

**Импорт чужих последовательностей.** DeepCAD/Text2CAD/SketchGraphs дают более разнообразные структуры. Ввести явную матрицу поддерживаемых операций, проверять геометрию до/после конвертации; неподдерживаемые конструкции не подменять молча.

**Teacher rollouts.** Сильная модель решает задачи в настоящем env; сохраняются действия и tool outputs, допускаются несколько кандидатов и retry. Положительные labels выдаёт verifier. Логировать и неуспешные попытки: они нужны для repair/preference и оценки стоимости. Не требуется сбор скрытых chain-of-thought рассуждений.

**Человеческие демонстрации.** Особенно полезны для GUI, инженерных стратегий и качественного holdout. FreeCAD macro/console log помогает понять вызовы API, но не заменяет запись экранов и состояния UI.

## 9. Формат хранения

Разделить `task.json` (что разрешено увидеть агенту), `reference/` (только verifier), `trajectory.jsonl` и артефакты. Внутри JSONL один event на шаг. Идентификаторы файлов — относительные пути внутри episode package или content-addressed URI; настоящие изображения хранить рядом, не подменять текстовыми placeholders.

Минимальный набор полей:

```json
{
  "schema_version": "cad-env.episode.v1",
  "episode_id": "flange-000042-edit",
  "task_type": "edit",
  "parent_model_id": "flange-000042",
  "family_id": "flange",
  "template_id": "flange-sketch-pocket-pattern-v1",
  "seed": 42,
  "units": {"length": "mm", "angle": "deg"},
  "backend": "freecad",
  "runtime_manifest": "runtime.json",
  "task": {
    "instruction": "Увеличь диаметр центрального отверстия с 10 до 12 мм, сохрани остальные размеры.",
    "initial_document": "input.FCStd",
    "observation_mode": "state_and_render",
    "action_mode": "structured_tools"
  },
  "trajectory": "trajectory.jsonl",
  "candidate_document": "output.FCStd",
  "validation_report": "validation.json",
  "provenance": {"source": "procedural", "generator_version": "flange-v1"},
  "split_group": "flange-template-lineage-000042"
}
```

Это **предлагаемая схема**, а не существующий проверенный эпизод. `runtime.json` должен содержать реальные версии/build/digest. `validation.json` — отдельно `execution_ok`, `recompute_ok`, `shape_valid`, `spec_pass`, `editability_pass`, значения/допуски по каждому требованию и `evaluator_error`.

Event содержит `step_id`, `observation_before`, фактический `action` и аргументы, `tool_result`, `observation_after`, artifact hashes, duration и флаги завершения. Для edit/repair обязательно фиксировать исходный документ и целевые изменения. Для GUI добавлять координаты/размер экрана, selection, workbench и путь скриншота.

SFT и VLM chat-форматы формировать как отдельные экспорты из этих событий. Обучать модель предсказывать assistant actions, маскируя user/system/tool targets в loss. Приватные reference labels и полный целевой код не должны попадать в вход агента при тестировании.

## 10. Проверка CAD и reward

### Обязательные уровни

1. **Исполнение:** программа закончилась в рамках бюджета; worker вернул структурированный результат; нужный документ существует и заново открывается.
2. **Состояние:** recompute не оставил ошибочные features, итоговый объект не пустой, заданное число тел, валидная геометрия и положительный объём там, где требуется solid. Эскиз/поверхность оцениваются по иному контракту.
3. **Спецификация:** проверка размеров, отверстий, положений, количества элементов, соосности и других явно заданных отношений.
4. **Геометрия:** volumetric IoU/симметрическая разность при надёжных boolean, surface distance/Chamfer с зафиксированным sampling, bbox и placement. Размеры и объём сами по себе не доказывают правильность формы.
5. **Параметричность:** нужные свойства представлены редактируемыми features/constraints; при контролируемом изменении параметра документ успешно перестраивается и сохраняет инварианты.
6. **Редактирование:** требуемое изменение достигнуто, остальные защищённые размеры и features сохранены. Геометрически похожий импортированный solid не должен проходить за параметрическое решение.

Не сравнивать исходный код как основную метрику: одна деталь имеет несколько корректных программ. Для открытых design задач не навязывать единственную reference-геометрию; оценивать заданные constraints и допустимое множество решений.

На первых этапах возвращать **вектор метрик и прозрачный бинарный `task_success`**. Для RL позже определить terminal reward через обязательные gates и нормированные scores геометрии/спецификации/редактируемости. Невалидный solid или нарушение обязательного требования обнуляет terminal success. Стоимость шагов учитывать отдельно; веса и tolerances калибровать на наборе хороших и намеренно плохих решений.

Dense reward вводить осторожно: вознаграждение за число объектов или вызов `recompute()` легко оптимизируется без решения задачи. Если добавлять shaping, использовать проверяемый прогресс по требованиям, ограничить бонусы и сохранять доминирование конечного результата. Agent не получает reference файлы или доступ на запись в verifier. Ошибку инфраструктуры evaluator хранить отдельно от неуспеха модели и никогда не превращать в положительный label.

## 11. Splits и исследовательский benchmark

Разделение выполнять **до** парафразов, рендера, мутаций и rollout-сбора. Группировать по происхождению/parent ID и структурному шаблону. Варианты одного оригинала не должны пересекать train/test. Сохранять исходные official splits внешних данных и проверять пересечение между корпусами; Text2CAD и DeepCAD имеют общее происхождение.

Нужны отдельные проверки:

- новые параметры в известных семействах;
- новые комбинации операций и длина последовательности;
- полностью новые семейства/шаблоны;
- редактирование и восстановление после ошибки;
- разные виды, камеры и темы UI для VLM;
- реальные или вручную подготовленные чертежи вместо только синтетических рендеров.

Внешние CADWorld и Parametric CAD Bench оставить контрольными наборами. При наличии пересечения исходных моделей исключать их производные из обучения. Отдельно сообщать success@1 и успех после разрешённых repair-попыток, шаги, wall time, стоимость, crash/timeout rate. Не удалять неудобные провалы из знаменателя.

Минимальные baseline: procedural oracle; замороженная code LLM; та же LLM с tools и feedback; VLM с изображениями. Затем абляции: state-only против state+render, Python против structured tools, SFT против SFT+repair, собственная синтетика против смеси источников. Выбирать модель после этого сравнения и оценки бюджета; текущий DialoGPT preset не является обоснованным CAD baseline.

## 12. План реализации с проверяемыми результатами

Объёмы ниже — предлагаемые цели пилота, не оценка уже доступных данных и не обещание сроков.

### Этап 0: достоверный backend

Зафиксировать runtime image; заменить silent simulation явными backend modes; реализовать worker handshake и прямые обработчики 6–10 действий. Отдельные статусы исполнения/геометрии/задачи; save/reopen; timeouts и crash recovery.

**Критерий:** 20 небольших эталонных программ повторно строятся с совпадающими метриками; синтаксическая ошибка, пустой результат, неверный размер и timeout различаются. Mock не может выдать geometry validation pass.

### Этап 1: gold benchmark и recorder

50–100 задач по 5–8 семействам, с ручной проверкой oracle и независимыми predicates. Покрыть create/edit/repair, границы диапазонов и отрицательные случаи. Сохранять checkpoints и машинные отчёты; убедиться, что verifier отклоняет похожие, но неправильные детали.

**Критерий:** можно воспроизвести эпизод в чистом worker и получить тот же вердикт; test groups исключены из будущей генерации.

### Этап 2: первая фабрика данных

Сгенерировать 1 000 параметрических моделей для проверки качества, затем при успешном аудите масштабировать до 10 000. Для иллюстрации ёмкости: 10 000 моделей × 8 смысловых шагов = 80 000 переходов; × 4 изображения состояния ≈ 320 000 кадров, без дополнительных before/edit кадров. Это потенциальное число записей, не число независимых моделей и не замер производительности.

**Критерий:** у каждого принятого положительного примера есть реальный FCStd, replay, provenance, validation и split group. Наличие файла/успех генератора не заменяет эти проверки. Публиковать yield принятых моделей и распределение причин отказа.

### Этап 3: VLM и адаптация моделей

Добавить multi-view renders, grounding, простые размерные чертежи. Получить baseline, провести LoRA/SFT подходящей code LLM/VLM, добавить реальные repair-rollouts. Сравнить с замороженной моделью на неизменном holdout. Long-context и multimodal packing подбирать по измеренной длине траекторий; текущие 512 токенов могут обрезать сценарии.

**Критерий:** улучшение CAD task success при фиксированных tools, бюджете и evaluator, с отдельным отчётом по unseen families.

### Этап 4: teacher sampling, preference и RL

Для одной задачи собирать несколько кандидатов. Обучать на проверенных успешных траекториях и на исправлениях; preference пары сравнивать при одинаковом входе/начальном состоянии. RL начинать с уже обученной политики, надёжного терминального reward и небольших batch. Отдельно учитывать расходы на неуспешные CAD запуски и рендеры.

### Этап 5: GUI

Пинованный FreeCAD desktop/VM, reset snapshots, recorder, небольшое число проверенных GUI skills и human/teacher demonstrations. Проверить через CADWorld-подобную схему оценки сохранённого документа. Сравнивать GUI-only и hybrid как разные режимы.

## 13. Измерения перед масштабированием

В пилоте измерить среднее/p95 время построения, проверки и рендера; peak RAM, bytes/model, acceptance yield и затраты teacher tokens. CPU/память нужны для CAD и rendering, GPU — для локального inference/training, а не как обязательное условие каждого geometry worker.

Время фабрики можно оценивать как `N_attempts × mean_pipeline_seconds / workers` с поправкой на загрузку, последовательные стадии и отказы; `N_attempts ≈ N_accepted / acceptance_yield`. Хранилище — число моделей × средний размер FCStd/checkpoints/кадров. Числа для бюджета должны появиться из пилота, а не из предположения о скорости FreeCAD.

## 14. Какой первый результат делать в этом репозитории

Первый implementation milestone: **одна пластина с параметрическим эскизом, Pad и Pocket**, записанная пошагово настоящим FreeCAD worker. Из неё автоматически получить:

- текстовую задачу создания;
- четыре вида для VLM;
- задачу изменения диаметра отверстия;
- задачу исправления неверного размера;
- полную траекторию с FCStd checkpoints;
- независимый отчёт проверки геометрии, требований и редактируемости.

Такой вертикальный прототип проверит всю ключевую гипотезу проекта. После него расширять библиотеку семейств и только затем объём корпуса. Рабочий код проекта в рамках этого исследования не менялся.
